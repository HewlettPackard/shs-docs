
# Known Issues

|:--:|:---------|:---------|
|3794828|ROCm 7.13 RCCL performance degradation in some multi-GPU workloads.|Set HSA\_NO\_SCRATCH\_RECLAIM=1 before launching the application.|
|3711515|ROCm and Ubuntu fails - amdkfd\_query\_rdma\_interface|No workaround for libcxi utils.<br>  For libfabric, ensure DMABUF is used (this is the default).<br>  FI\_HMEM\_ROCR\_USE\_DMABUF=1|
|3390017|GH200 LL128 Data Corruption Due to Unordered GPU Write Paths (GDRCopy Eager + Raw RDMA IOVA)|We recommend that to work around this, you set the following two environment variables, which avoid using the eager protocol in libfabric and instead use the rendezvous protocol:<br>  <br>  export FI\_CXI\_RDZV\_THRESHOLD=0<br>  export FI\_CXI\_RDZV\_GET\_MIN=0|
|3364924|PCIe timeout and AER errors causing instability on Perry Peak nodes with HPE Slingshot 200Gbps NIC-Switch ASIC|On Perry Peak nodes with HPE Slingshot 200Gbps NIC-Switch ASIC PCIe connectivity, failures are observed during SHMEM benchmarks, specifically the PUT\_NB\_lsheap test. A high volume of non-blocking PUT operations between random PEs leads to PCIe congestion. Cassini1 NIC reports AER errors, such as Completion Timeout, Unexpected Completion, and Header Log Overflow, which eventually cause a kernel crash.<br>  Additionally, responses for HPE Slingshot 200Gbps NIC requests to host memory exceed the configured completion timeout range (Completion Timeout), though the response eventually returns (Unexpected Completion).<br>  System Workaround:<br>  The issue is triggered by excessive outstanding non-blocking PCIe transactions, which increase latency and cause timeouts. Reducing PCIe load (e.g., throttling operations or introducing periodic synchronization like shmem\_quiet) improves stability.<br>  <br>  BIOS Workaround (Recommended):<br>  <br>  Apply BIOS/PCIe configuration updates<br>  ParryPeak supports Gen4ESM (20GT/s). Enable ESM firmware on HPE Slingshot 200Gbps NIC to run at 20GT/s (instead of 16GT/s)<br>  Increase PCIe Completion Timeout range|
|3127871|System crashed and rebooted while running iperf traffic with repeated hsn0 MTU change from (1500 - 9000)|When changing MTU size with high amount of traffic can crash the kernel.|
|2802789|Slingshot 400GB Switch: The assignment of AMA to the HSNx interface requires rebooting nodes.|For Slingshot 400GBps Switches:  <br>  <br>  All the assigned MAC addresses on node HSNx interfaces start with 02:XX:XX:XX:XX:XX<br>  If baseMacPrefix is changed to "06" HSNx AMA addresses on the nodes start with 06:XX:XX:XX:XX:XX<br>  <br>  To get AMA assigned to the HSN interfaces, it requires all the connected nodes to the switch fabric to be rebooted.|
|2215092|libfabric MR cache with memhooks may deadlock with CUDA and ROCM/ROCR|When doing RDMA with device memory, memhooks cannot be used as the system memory monitor. Either userfaultfd or HPE provided kdreg2 need to be used. The following environment variables are used to select these two memory monitors respectively.<br>  FI\_MR\_CACHE\_MONITOR=userfaultfd<br>  FI\_MR\_CACHE\_MONITOR=kdreg2|
|2191115|cxil\_destroy\_svc fails with EBUSY after all processes have exited|CXI Services can only be deleted once all associated NIC resources are released. In some cases, pending network operations or cleanup tasks may still be using these resources, which can temporarily prevent the deletion of a CXI Service. WLMs may be configured to extend the amount of time they attempt to free a CXI Service, or the clean\_cxi\_services.sh script provided by ATOM can be used.|

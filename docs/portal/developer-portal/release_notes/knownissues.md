|3429278|Multiple conflicting calls to hsa\_init with ROCm 7.12 and pytorch due to missing symlink|This is a known ROCm issue.<br>  Apply the following workaround:<br>  ln -sf /opt/rocm/core /opt/rocm/core/\_rocm\_sdk\_core<br>  touch /opt/rocm/core/\_rocm\_sdk\_core/\_\_init\_\_.py<br>  export PYTHONPATH=/opt/rocm/core:$PYTHONPATH|
|3417159|Hang and premature barrier-escape observed in TEST\_barrier\_verify|No immediate workaround. Issue is observed at higher node scales (≥25 nodes) and is not reproducible at lower scales or on other systems. Avoid running TEST\_barrier\_verify at large scales if encountered. A fix is planned for the next release to harden RDMA Get retry logic and prevent premature exit.|
|3364924|PCIe timeout and AER errors causing instability on Perry Peak nodes with HPE Slingshot 200Gbps NIC-Switch ASIC|On Perry Peak nodes with HPE Slingshot 200Gbps NIC-Switch ASIC PCIe connectivity, failures are observed during SHMEM benchmarks, specifically the PUT\_NB\_lsheap test. A high volume of non-blocking PUT operations between random PEs leads to PCIe congestion. Cassini1 NIC reports AER errors, such as Completion Timeout, Unexpected Completion, and Header Log Overflow, which eventually cause a kernel crash.<br>  Additionally, responses for HPE Slingshot 200Gbps NIC requests to host memory exceed the configured completion timeout range (Completion Timeout), though the response eventually returns (Unexpected Completion).<br>  System Workaround:<br>  The issue is triggered by excessive outstanding non-blocking PCIe transactions, which increase latency and cause timeouts. Reducing PCIe load (e.g., throttling operations or introducing periodic synchronization like shmem\_quiet) improves stability.<br>  <br>  BIOS Workaround (Recommended):<br>  <br>  Apply BIOS/PCIe configuration updates<br>  ParryPeak supports Gen4ESM (20GT/s). Enable ESM firmware on HPE Slingshot 200Gbps NIC to run at 20GT/s (instead of 16GT/s)<br>  Increase PCIe Completion Timeout range|
|3323446|Ubuntu (HPCM): Slingshot services do not auto-run due to HPCM networkd limitation|Due to an HPCM issue on Ubuntu, Slingshot services are not automatically configured or restarted. Administrators must manually intervene:<br>  <br>  On HSN interface run:<br>  <br>  systemctl restart slingshot-ama<br>  systemctl restart slingshot-ifroute<br>  <br>  <br>  Ensure the image is pre-configured with a systemd service to load Slingshot drivers at boot (manual setup required during image preparation)|

|2215092|libfabric MR cache with memhooks may deadlock with CUDA and ROCM/ROCR|When doing RDMA with device memory, memhooks cannot be used as the system memory monitor. |2191115|cxil\_destroy\_svc fails with EBUSY after all processes have exited|CXI Services can only be deleted once all associated NIC resources are released. In some cases, pending network operations or cleanup tasks may still be using these resources, which can temporarily prevent the deletion of a CXI Service. WLMs may be configured to extend the amount of time they attempt to free a CXI Service, or the clean\_cxi\_services.sh script provided by ATOM can be used.|
